\section{Higher-order goal%
  \BvrHint{\ldots secondary framing}}

The goal of \textbf{Smart Photo Drive} is to simplify the process of
finding personal photographs from large collections of event
photographs. Events such as college functions, conferences,
festivals, and other gatherings can generate hundreds or thousands of
photographs, making manual searching inconvenient and time-consuming.

The immediate engineering objective is to develop a web-based system
that uses computer vision to identify photographs containing a
particular user and present those photographs through an easy-to-use
interface.

The project focuses on combining an AI-assisted image retrieval
workflow with practical software engineering principles such as
modular design, authentication, database management, testing,
scalability, and deployment.

\section{Time-to-value%
  \BvrHint{\ldots primary heuristic}}

\begin{itemize}[leftmargin=0.7cm]

    \item We will first develop the basic end-to-end workflow in which
    event photographs can be uploaded and a user can search for
    photographs containing their face.

    \item Development will be carried out incrementally, beginning with
    a working prototype and then improving recognition quality,
    usability, performance, security, and deployment.

    \item Early iterations will prioritize a functional workflow so
    that the core idea can be tested using a controlled collection of
    event photographs.

    \item Feedback obtained during development and testing will be used
    to refine both the user interface and the photo retrieval process.

\end{itemize}

\section{Problem Statement}

Large events often result in a very large number of photographs being
captured by photographers. After the event, participants usually have
to manually browse through these photographs to find the images in
which they appear.

Common problems include:

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{Manual searching:} Users may need to inspect a large
    number of photographs individually.

    \item \textbf{Time consumption:} Finding a specific person's
    photographs becomes increasingly difficult as the collection
    grows.

    \item \textbf{Lack of person-based retrieval:} Conventional
    photograph folders are generally organized by event, date, or
    filename rather than by the people appearing in the photographs.

    \item \textbf{Repeated effort:} Multiple participants may
    independently perform the same manual search.

    \item \textbf{Large photo collections:} Event photographers and
    organizers need an efficient way to manage and distribute large
    numbers of photographs.

\end{itemize}

\textbf{Why this matters now:} The increasing use of digital
photography has made it easy to generate large event collections.
However, finding an individual's photographs within these collections
still requires significant manual effort.

\section{Proposed Solution%
\BvrHint{\ldots Software Proposition}}

\subsection{Overview}

Smart Photo Drive will be developed as a \textbf{web-based AI-assisted
photo retrieval system}. An event photographer or event manager will
be able to upload photographs from an event, while users will be able
to provide a reference photograph containing their face.

The system will process the event photographs and identify photographs
that are likely to contain the queried user.

The proposed system will contain the following major components:

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{Event management:} Event managers can create events
    and upload the corresponding photograph collection.

    \item \textbf{User photo search:} A user can provide a reference
    photograph to initiate the retrieval process.

    \item \textbf{Face recognition:} Computer vision techniques will
    be used to identify and compare faces present in photographs.

    \item \textbf{Photo retrieval:} Photographs containing matching
    faces will be identified and returned to the user.

    \item \textbf{Photo viewing:} Users will be able to view the
    photographs retrieved for them and access permitted downloads.

    \item \textbf{Role-based access:} Different workflows will be
    provided for normal users and event managers.

\end{itemize}

\subsection{Core workflow}

\begin{enumerate}[leftmargin=0.7cm]

    \item An event manager creates an event and uploads the event
    photographs.

    \item The system processes the uploaded photographs and detects
    faces present in the images.

    \item A user registers or logs in and provides a reference
    photograph containing their face.

    \item The system extracts relevant facial information from the
    reference photograph.

    \item The reference information is compared with faces identified
    in the event photographs.

    \item Photographs satisfying the selected matching criteria are
    retrieved.

    \item The matched photographs are displayed to the user through
    the web interface.

\end{enumerate}

\subsection{Operational constraints}

\begin{itemize}[leftmargin=0.7cm]

    \item The system should remain usable on commonly available
    desktop and mobile devices.

    \item The initial implementation will focus on manageable event
    collections while keeping the architecture extensible.

    \item The recognition process should provide a reasonable balance
    between accuracy and computational requirements.

    \item User photographs and event resources should be protected
    through appropriate authentication and access controls.

    \item Only information required for the application's operation
    should be collected and stored.

\end{itemize}

\section{Solution Approach%
  \BvrHint{\ldots Engineering focus}}

This is an engineering course project, so the focus will be on
integrating established technologies into a complete software system
rather than developing a new face-recognition algorithm.

\subsection{Face recognition and image processing}

The project will investigate established computer vision techniques
for detecting and recognizing faces.

OpenCV will be considered for image processing and supporting computer
vision operations. The \texttt{face\_recognition} library, which is
based on dlib, will be evaluated for generating facial encodings and
performing face comparisons.

The exact recognition configuration and matching threshold will be
determined during implementation and testing using representative
event photographs.

Factors such as lighting, image quality, pose, facial orientation,
and partial occlusion will be considered during evaluation.

\subsection{Web architecture%
  \BvrHint{\ldots proposed technology stack}}

The proposed system will follow a modular web architecture consisting
of a frontend, backend, database, image storage, and AI-processing
components.

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{Frontend:} React will be used for developing the
    interactive web interface. Vite will be used as the frontend
    development and build tool, while Tailwind CSS will be considered
    for responsive interface styling.

    \item \textbf{Backend:} Flask will be used to develop the backend
    APIs and application logic required for authentication, event
    management, photo processing, and retrieval.

    \item \textbf{Database:} MongoDB will be used for storing
    application information such as users, events, photograph
    metadata, and processing information.

    \item \textbf{Image storage:} Cloud-based object or image storage
    will be evaluated for storing large photograph collections
    separately from application metadata.

    \item \textbf{AI processing:} The face recognition and image
    processing components will interact with the backend to process
    photographs and provide retrieval results.

\end{itemize}

\subsection{Authentication and access control}

The system will provide separate workflows for its primary roles:

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{Users:} Users will be able to register, authenticate,
    search for photographs, and access photographs associated with
    permitted events.

    \item \textbf{Event Managers:} Event managers will be able to
    create events, upload photographs, and manage event-related
    resources.

\end{itemize}

Token-based authentication such as JSON Web Tokens (JWT) will be
considered for secure authentication. Passwords will be protected
using an appropriate password-hashing mechanism rather than being
stored directly.

\subsection{Development and deployment}

The project will use GitHub for version control and collaborative
development.

The application will be designed so that the frontend and backend can
be deployed independently. Docker will be considered for
containerizing backend services and creating a consistent development
and deployment environment.

The frontend can be deployed using a modern cloud hosting platform,
while the backend can be deployed using a suitable container-hosting
service.

\subsection{CI/CD and development automation}

GitHub Actions will be considered for automating repetitive software
engineering tasks during development.

Potential automated tasks include:

\begin{itemize}[leftmargin=0.7cm]

    \item running backend tests,
    \item validating the frontend build,
    \item checking code changes,
    \item building deployment artifacts, and
    \item supporting repeatable deployment processes.

\end{itemize}

The exact CI/CD workflow will be finalized as the project progresses.

\section{Evaluation Criterion%
  \BvrHint{\ldots measurable and attributable}}

The system will be evaluated using metrics related to recognition
quality, retrieval performance, and usability.

\subsection{Primary evaluation metric}

\textbf{Photo retrieval precision:} the proportion of photographs
returned by the system that actually contain the queried user.

A manually verified test collection will be used to compare the
system's retrieved results with the expected photographs.

\subsection{Secondary evaluation metrics}

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{Recall:} percentage of relevant photographs
    successfully retrieved.

    \item \textbf{False-match rate:} percentage of retrieved
    photographs that do not contain the target user.

    \item \textbf{Retrieval time:} time required to return matching
    photographs after a search request.

    \item \textbf{Processing time:} time required to process a
    collection of event photographs.

    \item \textbf{User experience:} ease with which users can upload a
    reference photograph and access their results.

    \item \textbf{System reliability:} successful completion of
    authentication, upload, processing, search, and retrieval
    operations during testing.

\end{itemize}

\subsection{Pilot validation plan}

\begin{itemize}[leftmargin=0.7cm]

    \item Prepare a representative collection of event photographs
    containing multiple individuals.

    \item Select several test users and provide reference photographs
    for them.

    \item Compare retrieved photographs with manually verified
    photographs.

    \item Measure retrieval and processing time for different
    collection sizes.

    \item Collect basic feedback from users regarding the simplicity
    and usefulness of the retrieval process.

\end{itemize}

\section{Scalability%
  \BvrHint{\ldots with foresight}}

The proposed architecture should remain capable of handling increasing
numbers of users, events, and photographs.

\begin{enumerate}[leftmargin=0.7cm]

    \item \textbf{Scalable architecture:}

    \begin{itemize}[leftmargin=0.7cm]

        \item Separate frontend and backend responsibilities.

        \item Store large image files separately from application
        metadata.

        \item Process photographs in batches where appropriate.

        \item Store useful processing results to avoid unnecessary
        repeated computation.

        \item Use pagination and efficient database queries for large
        collections.

    \end{itemize}

    \item \textbf{Deployment scalability:}

    \begin{itemize}[leftmargin=0.7cm]

        \item Use cloud-based infrastructure where required.

        \item Containerize backend components for consistent
        deployment.

        \item Keep storage and processing components modular so they
        can be scaled independently if required.

    \end{itemize}

\end{enumerate}

\section{Engine availability heuristic}

The project can be implemented using mature and widely available
software technologies. The initial technology direction includes:

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{React, Vite, and Tailwind CSS} for the frontend.

    \item \textbf{Flask} for backend APIs and application logic.

    \item \textbf{MongoDB} for application and event metadata.

    \item \textbf{OpenCV and face\_recognition/dlib} for computer

    \item \textbf{JWT-based authentication} and secure password

    \item \textbf{Cloud or object storage} for large photograph
    collections.

    \item \textbf{Docker} for reproducible deployment environments.

    \item \textbf{GitHub Actions} for development automation and
    continuous integration.

\end{itemize}

These technologies provide a practical starting point, while
implementation details and alternative tools will be evaluated during
subsequent development iterations.

\section{Risks and mitigations}

\begin{itemize}[leftmargin=0.7cm]

    \item \textbf{Face recognition accuracy:} Differences in lighting,
    pose, image quality, and occlusion may result in incorrect or
    missed matches. Testing with representative photographs and
    threshold evaluation will be used to improve reliability.

    \item \textbf{Large photo collections:} Processing a large number
    of photographs may require significant computational resources.
    Batch processing and efficient storage of processing results will
    be investigated.

    \item \textbf{Privacy:} Event photographs and facial information
    require appropriate protection. Authentication and access control
    will be implemented to restrict access to authorized resources.

    \item \textbf{Storage requirements:} Large event collections may
    require significant storage capacity. Cloud or object storage
    solutions will be evaluated according to project requirements.

    \item \textbf{Security:} Incorrect authentication or authorization
    could expose private photographs. User and event-manager
    permissions will therefore be tested separately.

    \item \textbf{Deployment complexity:} Integration of the
    frontend, backend, database, AI processing, and storage components
    may introduce deployment challenges. Containerization and
    automated testing will be introduced incrementally.

    \item \textbf{Evaluation ambiguity:} Recognition quality will be
    evaluated using a manually verified test collection and measurable
    metrics such as precision, recall, and false-match rate.

\end{itemize}

\section{Summary}

This project proposes \textbf{Smart Photo Drive}, a web-based
AI-assisted system for automatically finding photographs of a user
from large collections of event photographs.

The proposed workflow allows an event manager to upload an event photo
collection while users provide a reference photograph containing their
face. Computer vision techniques are then used to identify likely
matching photographs, which are presented through the web interface.

The initial technology direction includes React, Vite, and Tailwind
CSS for the frontend, Flask for the backend, MongoDB for application
data, and established computer vision libraries for face processing.
Cloud-based storage, authentication, containerization, and automated
development workflows will be incorporated as the project progresses.

The project emphasizes software engineering principles including
incremental development, modular architecture, authentication,
testing, measurable evaluation, scalability, version control, and
deployment.

The final objective is to replace the manual process of searching
through large event photo collections with a faster, automated, and
user-friendly photo retrieval experience.
